## 2. 측정값 (로그 타임스탬프)

- 왕복 1회: 평균 약 6~9초 (가져오기 1.9~9초 + 사이트 이동/재계획 1~6초)
- 문(site -1 → 1): 처음부터 건설 시작까지 **190초**, 왕복 16회, 실패 1회 포함
- 벽틀 1개(site 5): 사이트에 재료가 있을 때 2초
- 단계마다 `SETTLE_MS = 400`ms 대기 + MP에서는 아이템 이동 1개씩 순서대로(`oneAtATime`)
- `fetch took ... from c:5951,5249`처럼 같은 상자를 연속으로 다녀옴 → 한 번에 여러 개를 가져갈 수 있었던 경우

- 문 재료 합계 ≈ 4 + 0.2 + 1 + 1 = **6.2** (망치 제외). 테스트 주석에 "기본 한도는 판자 2개 정도"라고 되어 있음 → 맨손 인벤토리로는 문 하나에 최소 3~4번 왕복.
- 가방에 넣으면 무게 감소가 적용되어 같은 재료를 1~2번에 운반 가능.

## 4. 시스템 비용 (모드 코드)

- **claim 폭주**: `F.advance`가 가져오기 단계마다, 사이트 단계마다 `BuildAhead.claim` 호출 → MP에서 `claim` 명령 전송 → 서버는 `BuildAheadSites.claim`이 항상 true라서 **매번 전체 사이트 목록을 모든 클라이언트에 `ModData.transmit`** → 각 클라이언트는 받을 때마다 `cache` 전체 삭제 → 모든 고스트의 엔티티를 다시 만듦(`makeEntity` + `autoPopulateInputs`). 왕복 1회당 2번, 사이트 수 × 플레이어 수에 비례.
- 스캔: 운반 시작/재계획마다 41x41 = 1,681칸 새로 스캔(캐시 안 씀). 고스트 색 계산은 61x61 = 3,721칸 스캔을 2초 재사용.
- `hasMaterialsNow` / `freshContainers`: 재계획마다 루트창 새로고침.
- 프레임 예산: `GATHER_PER_FRAME = 2`, `STATES_PER_FRAME = 8`.

## 5. 개선 방향 (아이디어, 미구현)

게임 효율
1. 운반 용량: 착용한 가방을 포함해 남은 무게를 계산하고, 가방으로 바로 옮기기. 과적 상태에서도 가벼운 것(못, 경첩)은 묶어서 가져가기.
2. 사이트별 서는 칸 고정: 처음 고른 칸(경로로 닿는 칸)을 job에 저장해 매번 같은 칸으로 가고, 그 칸 3x3에 내려놓기. 그 3x3은 "이미 있는 재료"로 세고 공급처에서 제외 → P3 해결.
3. 서는 칸은 `FindWall`의 직선거리 대신 실제로 닿는 쪽(현재 칸과 같은 쪽, 또는 경로 비용)으로 직접 고르고 `ISPathFindAction`으로 이동 → P5 해결.
4. `MAX_TRIPS`를 고정 10회 대신 "진척 없는 왕복 N회"로 바꾸기.
5. 한 공급처에서 여러 사이트의 재료를 한 번에 가져오기(가까운 벽틀 여러 개).

시스템
6. claim은 상태가 바뀔 때만 전송, 서버도 바뀌었을 때만 transmit (이미 내 claim이고 시간이 충분히 남았으면 생략).
7. ModData 수신 시 cache 전체 삭제 대신 바뀐 사이트만 무효화.
8. P4 진단: "materials not usable"일 때 두 기준의 결과(입력별 부족분, 도구 상태)를 로그에 남기기.
